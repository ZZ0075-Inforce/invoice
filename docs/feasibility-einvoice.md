# 台灣財政部電子發票 — 取得個人消費紀錄之可行性評估

- 評估日期：2026-07-26
- 目標：以程式自動取得「我個人」的電子發票消費紀錄（表頭 + 品項明細）
- 評估對象：(A) 財政部官方電子發票應用 API、(B) 網頁登入自動化、(C) 其他替代管道

---

## 0. 結論摘要（TL;DR）

| 路線 | 技術可行性 | 取得門檻 | 建議 |
|---|---|---|---|
| **A. 官方 API** | 高（規格完整、有免費流量） | **極高 — 自 112/3/31 起自然人不得申請，開發者須具 ISO27001/CNS27001 認證** | 個人專案基本走不通；有公司主體才考慮 |
| **B. 網頁登入自動化** | 中（需處理圖形驗證碼、平台改版風險） | 低（用自己的手機條碼 + 驗證碼） | **個人用途的務實首選，建議做成「半自動」** |
| **C. 平台 CSV 手動匯出 + 本地解析** | 高 | 極低 | **先做這個驗證資料品質**，也可能已足夠 |
| **D. MyData** | 低（偏單張查驗，非批次消費紀錄） | 中 | 不適合本需求 |

**核心結論：**

1. 官方 API **不是「免費額度」模式，而是「審核制」**。它不按量收費，流量上限對個人用途也綽綽有餘（每 AppID 每 10 秒 1500 次），但**申請資格已排除個人**——這是關鍵阻礙，不是技術問題也不是錢的問題。
2. 因此若你是以個人身分開發，**應採網頁登入自動化路線**（B）。這是登入你自己的帳號、取回你自己的資料，性質上是正常使用，但需自我限流並妥善保管憑證。
3. 動手前**先做 Phase 0**：手動從平台匯出一個月的 CSV，確認欄位與品項明細品質是否真的滿足你的需求。很多商家品項只上傳一筆「消費」，若你的目的是消費分析，這點可能直接決定專案值不值得做。

## 1. 路線 A：官方電子發票應用 API

### 1.1 與「個人消費紀錄」相關的 API

Base URL（正式）：`https://api.einvoice.nat.gov.tw`
測試環境：`https://wwwtest.einvoice.nat.gov.tw`

| action | Endpoint | 用途 | 認證 | 主要限制 |
|---|---|---|---|---|
| `carrierInvChk` | `POST /PB2CAPIVAN/invServ/InvServ` | **載具發票表頭清單**（發票號碼、日期、店家、金額、中獎狀態） | `appID` + 使用者載具憑證 | **起訖日期須為同一月份** → 每月一次呼叫 |
| `carrierInvDetail` | `POST /PB2CAPIVAN/invServ/InvServ` | **單張發票品項明細**（品名、數量、單價、金額） | `appID` + 使用者載具憑證 | **一次只能查一張** → N 張發票 = N 次呼叫 |
| `qryCarrierAgg` | `POST /PB2CAPIVAN/Carrier/Aggregate` | 查詢手機條碼底下已歸戶的載具清單 | `appID` + `signature` | — |
| `carrierInvDnt` | `POST /PB2CAPIVAN/CarInv/Donate` | 捐贈發票 | `appID` + `signature` | 本需求用不到 |
| `qryWinningList` | `POST /PB2CAPIVAN/invapp/InvApp` | 中獎號碼清單 | `appID` | 不涉個資，雙月開獎 |
| `qryInvHeader` / `qryInvDetail` | `POST /PB2CAPIVAN/invapp/InvApp` | 掃 QRCode / Barcode 查單張發票 | `appID` | `qryInvDetail` 需 `encrypt`、`sellerID`、`randomNumber` |
| ODS371I | `GET https://sip.einvoice.nat.gov.tw/ods-main/ODS371I/query` | 個人化消費統計（依日期／縣市／行業別彙總） | `appID` + `signature` | 僅彙總值，無單筆明細 |

**取得完整消費紀錄的實際流程：**

```
qryCarrierAgg          → 取得所有已歸戶載具
  └─ for 每個月份:
       carrierInvChk   → 該月發票表頭清單（1 call / 月）
         └─ for 每張發票:
              carrierInvDetail  → 品項明細（1 call / 張）
```

呼叫量估算：一年份、每月 40 張發票 → 12 + 480 ≈ **500 次呼叫**。相對於 1500 次/10 秒 的上限，完全不是問題。

### 1.2 認證模型（理解門檻為何這麼高的關鍵）

有**兩層**憑證，兩者都要：

1. **開發者憑證** — `appID`（Application ID）+ `APIKey`。向財政資訊中心申請核發。`APIKey` 用於部分 API 的 `signature`（簽章）計算。
2. **使用者憑證** — `cardType`（手機條碼固定為 `3J0002`；悠遊卡 `1K0001`、一卡通 `1H0001`、iBonus `2G0001`）、`cardNo`（載具號碼，如 `/ABC.123`）、`cardEncrypt`（**驗證碼，即你的平台登入密碼**）。

⚠️ **關鍵風險點**：`cardEncrypt` 是使用者的平台密碼，以一般 POST 參數傳送。也就是說，任何持有 appID 的第三方 App，只要使用者輸入了手機條碼與驗證碼，即可取得該使用者**全部**的消費明細，且該密碼與平台登入密碼相同。這正是財政部後續大幅提高開發者資格門檻（要求 ISO27001）的直接原因，也是**你不應把這組憑證交給任何第三方 App** 的理由。

> 註：`carrierInvChk` / `carrierInvDetail` 在較舊的規格（v0.5）中僅需 `appID`；規格已迭代至 v1.9（112/8）與 **v2.0（113/5/31）**，部分載具類 API 已加上 `signature` 要求。實際實作時**務必以最新版規格為準**。

### 1.3 費用與流量

- **無按量計費、無「免費額度」概念**。官方未公告任何 API 收費機制，取得授權後即可使用。
- **流量管制**：自 **113/6/20** 起，每一 AppID 請求以 **10 秒內 1500 次**為上限，逾上限者暫停該 AppID 請求 10 秒。
- 財資中心亦保留對單一 IP 或 AppID 於一定時間內連線達一定次數者進行流量管制之權利。

→ **就流量與費用而言，個人用途毫無壓力。瓶頸完全在「拿不拿得到 appID」。**

### 1.4 申請門檻（❌ 主要阻礙）

依《**電子發票應用程式介面使用規範**》（112/3/31 生效，並由原名稱修正更名）：

| 項目 | 規定 |
|---|---|
| 開發者資格 | 企業、組織或政府機關 |
| **個人（自然人）** | **不再列入開發者範圍** |
| 資安要求 | 資訊安全制度須通過 **CNS27001 國家標準或 ISO27001 國際標準**認證；**認證範圍須涵蓋利用 API 之軟體產品及加值衍生著作的所有資訊業務活動** |
| 法遵 | 須將本規範及稅捐稽徵法、個人資料保護法、營業秘密法等納入法規遵循清單 |
| 授權期間 | 最長 3 年；到期前 2～6 個月須重新申請審核 |
| 既有開發者 | 生效日前已核准者，須於生效日起 2 年內重新申請審核（即 **114/3/30** 前），逾期停止提供 API |
| 申請方式 | 向財政部財政資訊中心提出申請，審核通過後核發 AppID 與 APIKey |

**判定：ISO27001/CNS27001 認證僅適用於企業與組織，個人無從取得。個人專案走官方 API 的路已封閉。**

若你名下有公司主體，取得 ISO27001 認證的成本（顧問輔導 + 驗證）以本需求（一個私人記帳工具）而言，投入產出比明顯不合理。

### 1.5 資料涵蓋範圍的先天限制（不論走哪條路都適用）

這幾點會直接影響專案價值，請務必先確認：

- **只涵蓋「已存入載具」的雲端發票。** 紙本發票、未出示手機條碼的消費不會出現。
- **品項明細品質參差。** 明細由開票商家自行上傳，相當多商家只上傳一筆「消費」或「商品一批」，並無逐項品名。若你的目的是「消費分類分析」，這會是最大的實務落差。
- **明細（品項）保存期較短。** 平台上可查的發票明細約為**近 6 個月／近 3 期**；更早的消費明細須檢具身分證、載具影本與申請書向平台專案申請，審核後約 3 個工作天取得。
- **表頭資料可回溯較久。** 消費者可查詢**前 7 年及當年**的發票資料。
- **載具需先完成歸戶。** 悠遊卡、一卡通、會員卡等載具須歸戶至手機條碼，才會一併查得。

> 上述保存期限說明依公開資料整理，**建議在 Phase 0 以實測確認**（往回拉不同月份看資料何時斷掉）。

## 2. 路線 B：網頁登入自動化（個人用途建議方案）

### 2.1 登入方式

電子發票整合服務平台（`https://www.einvoice.nat.gov.tw`）消費者登入：

| 方式 | 自動化難度 | 說明 |
|---|---|---|
| **手機號碼 + 驗證碼(密碼) + 圖形驗證碼** | 中 | 唯一實務可自動化的方式，但有 CAPTCHA |
| 自然人憑證 | 高 | 需讀卡機與本機元件 |
| 健保卡 | 高 | 同上 |
| 行動自然人憑證（TW FidO） | 高 | 需手機 App 互動確認 |

→ 只有第一種可行。**圖形驗證碼是唯一的技術關卡。**

### 2.2 技術路徑

```
Playwright (本環境已預裝 Chromium)
  → 開啟登入頁
  → 填入手機號碼 + 驗證碼（自 keyring / env 讀取）
  → 圖形驗證碼：擷取圖片 → 人工輸入 or OCR/多模態模型辨識
  → 登入成功後保存 storage_state（cookie）供後續重用
  → 進入「載具發票查詢」
  → 逐月選取 → 匯出 CSV（優先）或直接解析表格 DOM
  → 正規化後寫入 SQLite，以發票號碼為唯一鍵做增量 upsert
```

**強烈建議做成「半自動」而非全自動**：只在 session 失效時提示人工輸入圖形驗證碼，其餘時間重用 cookie。理由——

- 避免建置 CAPTCHA 破解，法遵與道德上都乾淨得多。
- 個人記帳的更新頻率本來就低（每月一次即可），人工介入 30 秒的成本可以忽略。
- 大幅降低因自動化行為被平台判定為異常而鎖定帳號的風險。

### 2.3 風險與注意事項

| 風險 | 說明 | 緩解 |
|---|---|---|
| **平台改版** | 該平台曾大幅改版（現為 SPA，需 JavaScript），前端選擇器隨時可能失效 | 抓 CSV 匯出而非解析 DOM；為選擇器建立集中設定與失效告警 |
| **憑證安全** | 手機條碼驗證碼等同平台密碼，外洩即全部消費紀錄外洩 | 存於 OS keyring 或環境變數；`.gitignore` 嚴格排除；**絕不寫入 repo 或 log** |
| **帳號被鎖** | 高頻自動請求可能觸發防護 | 自我限流：每次執行只抓必要月份、請求間加延遲、每日最多執行一次 |
| **使用規範** | 登入自己的帳號取自己的資料屬正常使用；但自動化大量請求有影響平台效能之虞 | 保守限流、不做併發、不對外提供服務 |
| **⚠️ 絕對不要做** | 逆向官方 App 並盜用其 `appID` 呼叫 API | 明確違反《電子發票應用程式介面使用規範》，且涉及他人授權憑證之濫用 |

## 3. 路線 C／D：其他替代管道

### C. 平台手動 CSV 匯出 + 本地解析（建議先做）

平台支援**匯出指定月份的載具發票資料為 CSV**，內容含消費品項、金額、商家、日期等欄位。

- 優點：零技術風險、零法遵疑慮、立即可用。
- 缺點：每月需人工操作一次。
- **這也是 Phase 0 的驗證手段** — 用它確認資料品質後再決定要不要自動化。

### D. 財政部 MyData（個人化資料自主運用，`https://mydata.nat.gov.tw`）

提供「**手機條碼單一發票消費明細資料**」與「**發票驗證(電子發票)**」兩項與電子發票相關的服務。

- 性質偏向**單張發票查驗**，而非批次取回一段期間的消費紀錄。
- 介接（API 串接）對象通常為政府機關或特許業者，個人僅能自行至平台下載文件。
- **不適合本需求**，但可作為單張發票查驗的補充。

### 第三方 App（發票存摺 invos、雲端發票 box 等）

這些 App 持有合法 appID，功能完整（部分還提供比官方更長的明細保存期），但：

- 均不對外開放 API 供你程式化取用。
- 使用它們等同把手機條碼 + 驗證碼交給第三方（見 §1.2 的風險說明）。

## 4. 建議做法（分階段）

### Phase 0 — 資料品質驗證（半天，先做這個）

1. 手動登入平台，匯出最近 1～2 個月的載具發票 CSV。
2. 檢查：欄位有哪些？品項明細的覆蓋率如何（多少張發票有真正的品名）？金額／店家／日期是否完整？
3. 往回測試不同月份，實測明細與表頭各自能回溯多久。
4. **決策點**：若品項明細覆蓋率太低而你的目標是消費分析，應在此時重新定義需求（例如只做「店家 + 金額」層級的記帳），或直接放棄自動化。

### Phase 1 — 半自動抓取（2～3 天）

- Playwright 半自動登入（人工輸入圖形驗證碼）+ storage_state 重用。
- 逐月匯出 CSV → 解析 → SQLite（以發票號碼為主鍵做增量 upsert）。
- 憑證走 keyring / env，repo 內不留任何機敏資料。
- 內建限流與失敗重試上限。

### Phase 2 — 視情況擴充

- CLI／簡單報表／匯出到記帳工具。
- 若日後需長期穩定或多人使用 → 才回頭評估「公司主體 + ISO27001 + 官方 API」的正規路線。

## 5. 本次評估的限制與待你確認事項

**評估限制：**

- 本次執行環境的網路政策封鎖所有 `*.gov.tw` 網域，**無法實測登入流程與 API 端點**。上述端點、參數與限制係整理自官方 API 規格（OpenAPI 化版本）、《電子發票應用程式介面使用規範》及公開技術文件。
- API 規格已迭代至 **v2.0（113/5/31）**，本文部分參數細節取自較早版本的公開整理，**實作前請以官方最新規格 PDF 為準**。

**需要你確認的問題：**

1. 你有**公司／組織主體**嗎？（若有，官方 API 路線才值得重新評估）
2. 需要回溯**多久**的消費紀錄？（超過 6 個月的品項明細須專案申請）
3. 需要**品項明細**，還是「店家 + 金額 + 日期」層級就夠？
4. 這是**純個人自用**，還是未來會給其他人使用？（後者的法遵要求完全不同）
